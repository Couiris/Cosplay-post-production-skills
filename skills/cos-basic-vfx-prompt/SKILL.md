# COS 基础后期与 VFX 预设

把用户对一张 COS 照片的后期意图，转换成一份可执行、可校验、尽量少改无关内容的插件 JSON。默认交付一个外层预设；复杂请求仍放进同一预设，但用 `pass_plan` 给出有序微步骤，避免一次性重绘失控。

## 先判断是否适用

- 保留人物、姿态、机位和大部分原背景，只做局部修复、增材、特效、调色、换天或有限扩边：使用本 skill。
- 保留场馆墙顶但要清场并重铺地面/局部布景：改用 `$cos-semi-composite-prompt`。
- 大面积换背景、重建世界、添加巨型生物/建筑/载具：改用 `$cos-large-composite-prompt`。
- 只有无特效调色与常规精修分析、不需要插件 JSON：优先 `$cosplay-clean-retouch`。

判断核心是“新增像素面积和场景几何是否成为任务主体”，而不是用户是否说了“海报”“大片”。

## 不可突破的边界

- 不承诺生成模型能物理保证“逐像素不变”。把它写成目标、遮罩规则和验收条件；执行器没有局部蒙版或图层回贴能力时，将锁定可靠性标为 `best_effort` 并提示风险。
- 每个改动必须有 `authorized_area`、锚点/落点、深度、遮挡和边缘过渡；未授权区域是只读目标。
- 人物身份、人数、姿态、手势和坐标默认锁定。只有用户明确启用的修脸、塑形、风动、悬浮、分身或风格化模块，才开放对应单一维度。
- 去安全裤/打底裤穿帮只用裙摆、外层服装、阴影或同类丝袜继续覆盖；不减少身体覆盖、不生成裸露。
- 去水印只处理用户自有或获授权图片。不要协助移除来源标识以冒充权属。
- 不凭服装猜测不确定的官方设定、纹章或文字。低置信度时使用抽象几何、角色现有配色和中性母题，并写明推断。

每次生成预设时：

2. 读 [锁定合同](references/lock-contracts.md) 和 [输出格式](references/output-schema.md)。
3. 读 [模块注册表](references/module-registry.md)，只使用规范键名；旧键名仅作为输入别名。

按请求再读：

- 特效：读 [特效总库](references/effects-library.md) 与 [特效提示词编译器](references/effect-prompt-compiler.md)；涉及自发光、透明、体积或镜头效应时加读 [材质与光影](references/material-light.md)。
- 新增打光或多图溶图：读 [新增打光与溶图](references/lighting-and-blending.md)。

## 工作流

### 1. 读图与记录不确定性

若有照片，先写 `photo_readout`：真实人数、主体框、脸/手/脚点、可用负空间、遮挡、画布比例、透视线、焦平面、噪点/压缩、主光方向/软硬/冷暖及证据。看不清就写 `unknown` 或范围与置信度；不编造 EXIF、角色名或不可见材质。

若用户没给图，也要生成可导入预设，但将依赖图像判断的值写成“执行时从输入图检测”，不要假造坐标。

### 2. 建立执行器能力档案

在内层写 `executor_profile`：

- `target_family`: `nano_banana_or_gemini_image_edit`
- `mask_support`: `explicit | semantic | unknown`
- `multi_reference_support`: 用户或插件已说明时填写，否则 `unknown`；启用 `image_blend_plan` 时还要写每张供体图职责
- `text_rendering`: `supported | unknown | disabled`
- `output_size`: 用户明确时写 1K/2K/4K 或尺寸，否则 `match_input`
- `lock_reliability`: 有显式蒙版与底图回贴时 `strong`，只有自然语言语义蒙版时 `best_effort`

不要把当前 API 型号、参考图上限或分辨率能力写死在每个预设里；这些会变化。只有用户指定模型或插件已暴露能力时才选择特定配置。

### 3. 选择最少够用的模块

使用 [模块注册表](references/module-registry.md) 的规范键。一个请求只启用必要模块，不为“更高级”自动加磨皮、瘦脸、换色、调色或虚化。

按风险给每项计分：

- 1 分：局部清理、小范围颜色/质感、轻粒子、边框。
- 2 分：自发光特效、手/假发修复、服装结构修复、虚拟灯、局部溶图、换天、背景虚化、调色。
- 3 分：脸型/身形、分身/悬浮、多供体复杂溶图、明显风格化、扩图、精确文字、多主体交互。

总分不超过 6 且模块互不冲突，可 `single_pass`。超过 6、同时改身份邻域与全局风格、或包含多个高风险项时，仍输出一份预设，但 `execution_strategy` 设为 `ordered_micro_passes`，在 `pass_plan` 中依次写清修复、增材/VFX、全局成片；每一步都以前一步结果为输入并重新锁定未授权区域。

### 4. 先解决冲突再写提示词

锁定优先级：

`用户显式要求 > 身份与安全覆盖 > 姿态/坐标 > 相机几何 > 原背景 > 局部修复 > 增材/VFX > 全局影调 > 风格包装`

同一维度出现冲突时只保留高优先级意图。例如，用户既要“背景完全不变”又要“压暗背景”，把压暗背景列为显式例外；既要“姿态零偏移”又要“悬浮”，只开放整体 Y 位移并锁肢体角度。

### 5. 用五段式写每项修改

每个模块都写：

1. `goal`：最终画面要达到什么。
2. `preserve`：列出对本改动最关键的 3–6 个保留项，避免重复整份合同。
3. `change`：对象、区域、锚点、尺度、材质、颜色、强度和单一时间相位。
4. `integrate`：透视、遮挡、接触影/反射、主光关系、景深、噪点和边缘衰减。
5. `acceptance`：可观察的通过/拒绝标准与局部重试范围。

正向描述目标状态优先。例如用“街道保持空旷，仅有原建筑与地面”配合“移除指定路人”，不要依赖冗长的 `no/no/no` 串。`negative_prompt` 只收敛本次最可能的 8–20 个翻车点。

### 6. 特效、虚拟灯和溶图内容必须进入相机空间

- 自发光特效以原主光为主、特效光为次。写 `vfx_relight_mask`：可达面、颜色、最大亮度变化、距离衰减和遮挡终止。
- 贴地效果复用原地面透视；附着效果沿曲面/折痕；实体必须有尺度、承托、接触影和投影；透明体要写折射、菲涅尔和背景可见度。
- 近/中/远至少两层有差异，同深度新增物不能比原内容更锐更干净。
- 默认 1 个主效果 + 1 个环境响应 + 1 个空气层；发光主色不超过 3 种，除非用户明确要多彩风格。
- 新增虚拟灯逐灯写光源动机、方向、色温、软硬、范围、衰减、可达面与投影；不把全图染色当作打光。
- 多图溶图指定唯一底图，并为每张供体图列 `transfer_only/do_not_transfer`；底图人物与几何优先。供体成为大面积新场景时转合成 skill。

### 7. 文字与参考图

- `text_plan` 仅在用户明确要求文字时启用。保留用户给出的准确字符串、语言、大小写与标点，限制文字数量，并给出安全留白、层级、对齐和可读性验收。
- 能力未知或要求零错字时，默认 `render_text: false`，只生成排版安全区和文字图层说明；建议宿主软件排字。
- 有参考图时给每张图分配单一职责：`identity / costume / prop / color / composition / typography`。不得把参考图里的无关人物、姿态或场景搬入成片。
- 溶图额外使用 `base_image/donor_images/transfer_only/do_not_transfer`，底图是人物姿态与机位基准；大面积供体场景成为新世界时转合成 skill。

### 8. 组装并验证

外层必须含 `id/title/content/params/category/subCategory/refImages/_isFactory`；`content` 是单行 JSON 字符串。内层至少含角色指令、读图、执行器档案、三份锁定合同、光源档案、启用模块、授权并集、融入、执行策略、约束与负面词。

若保存为文件，运行：

```powershell
python scripts/validate_preset.py <preset.json>
python scripts/audit_skill.py
```

验证失败就修正后再交付。聊天内直接输出时也按相同规则自检，禁止省略号、注释、占位符或不存在的 `params.target`。

## 交付规则

- 默认在回答中给一份完整 JSON；用户明确要求保存时才写盘。
- JSON 前最多用 2–4 条短句说明关键假设、模块选择、光源判断和高风险执行策略。
- `id` 使用 `f_<category>_<kebab-slug>`；跨类组合用 `combo`。
- 未启用模块不写入 `content`，避免模型误执行。
- 不写“100% 保证不崩”。写清能力条件、风险、验收和只重试失败区域的办法。
